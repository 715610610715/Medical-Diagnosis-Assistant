# 项目分析与复盘：医疗诊断辅助系统

> 从「产品 + 技术 + 求职」三个视角，把项目讲清楚、讲诚实。

---

## 1. 一句话总结

**用 UMLS 医学知识库 + 传统机器学习，实现"输入症状 → 一次性输出疾病预测、相关症状建议、疾病详情"的辅助诊疗系统**，前端一键诊断，后端 5 个标准化 API，可 Docker 私有化部署。

## 2. 技术分析

### 2.1 系统架构

```
浏览器
  │
  ▼
Gradio 前端 app_gradio.py（一键诊断 / 手动模式）
  │  HTTP (localhost:7680/api)
  ▼
Flask 后端 app_1119.py
  ├─ /api/validateSymptom     症状名 → CUI（en_Labels.js 映射 + difflib 模糊匹配）
  ├─ /api/predict             症状CUI列表 → 疾病 + 概率（朴素贝叶斯）
  ├─ /api/predictFromString   症状名串 → 疾病（快捷方式）
  ├─ /api/sySuggest           CUI → 相关症状（CUI2Vec 余弦相似度）
  └─ /api/getDetails          CUI → UMLS 详情（umls.db）
```

### 2.2 模型是怎么来的？（重点，面试必问）

**疾病预测模型不是调外部 API，也不是大模型**，而是自己训练的朴素贝叶斯分类器：

1. **数据**：`disease-symptom-db.csv` + `DiseaseSymptomKB.csv`（疾病-症状关系数据，源自公开数据集/上游项目）。
2. **特征**：`train.py` 把"疾病-症状"表转成 one-hot 矩阵（每个症状一列，`all_x.csv`），用 `MultinomialNB`（多项式朴素贝叶斯）训练，保存为 `all_mnb.pkl`。
3. **推理**：运行时把输入症状的 CUI 在特征向量上置 1，调用 `predict_proba` 得到每种疾病的概率，按概率排序返回 Top15。
4. **为什么选朴素贝叶斯**：数据量不大、特征稀疏、可解释、训练快、离线可跑。医疗场景要"可解释"，NB 的朴素假设和概率输出都容易向用户解释。

**相关症状推荐**：`relatedSymptoms.py` 用 Keras 实现 skip-gram（Word2Vec 思路），在症状共现数据上训练出每个 CUI 的 50 维向量（`10_epochs_0.6_similarity.npy`），运行时算余弦相似度。

**疾病详情**：不是模型，是查 UMLS 数据库（`umls.db`，SQLite），返回标准术语信息。

### 2.3 诚实说明（面试前必须想清楚）

- 项目名叫"大模型"，但**当前实现没有调用任何大模型 API**，核心是"知识库 + 传统机器学习"。
- 结题报告里写的"接入开源大模型、UMLS 知识增强"更接近**产品愿景**，实际落地用的是 UMLS 标准化 + 传统模型。
- 面试时主动讲清楚这点反而加分：说明你理解"大模型"与"传统 ML + 知识库"的边界，并且已经规划好 V2 怎么把真正的 LLM Agent 接进来（意图识别 + 工具调用 + RAG）。

## 3. 产品与用户价值

- **对患者**：去挂号前先有初步判断，减少盲目就医。
- **对基层医生**：鉴别诊断的"第二意见"，降低漏诊风险。
- **对医学生**：可交互的症状-疾病知识图谱。

## 4. 竞品分析（简要）

| 竞品 | 特点 | 我们的差异点 |
| --- | --- | --- |
| 丁香医生 / 百度健康 | 内容 + 在线问诊，C端流量大 | 开源、可解释（概率+知识库）、可私有化 |
| 各类"AI医生"小程序 | 多为大模型对话 | 我们展示概率排序 + 标准术语，可追溯 |
| 医院 HIS 辅助决策 | 强合规、强业务绑定 | 轻量、低成本、适合学习与演示 |

## 5. 数据与效果

- 接口数量：5 个标准 REST API。
- 功能模块：一键诊断 + 4 个手动查询模块。
- 模型：MultinomialNB（疾病预测）+ CUI2Vec（症状相似度）。
- 知识库：UMLS（CUI 体系）约覆盖数万医学概念（以 umls.db 为准）。
- 部署：Docker，容器化一键启动（修复端口冲突后可稳定运行）。

> 说明：当前没有严格的线上准确率评测报告。简历和面试中建议表述为"实现了可解释的疾病预测排序"，不要写未经评测的准确率数字。

## 6. 项目复盘

### 做得好的
- 从 0 到 1 完成了"数据 → 模型 → API → 前端 → 部署"全链路。
- 用标准医学编码（CUI）解决了"同一症状多种叫法"的语义统一问题。
- 一键诊断把用户操作从 4 步降到 1 步，产品思维清晰。
- 全部容器化，可复现。

### 踩过的坑（都是面试好素材）
- **端口冲突**：Windows"传递优化"服务占用 7680，导致容器无法启动 → 学会用 `netstat` 定位进程、用改端口/重建容器解决。
- **环境复杂**：容器里 Python 3.6（后端）与 Conda Python 3.10（前端 Gradio）共存 → 理解了多版本环境隔离。
- **中文症状支持差**：后端数据是英文术语 → 在前端加中文→英文映射。
- **数据获取难**：UMLS 数据库 2.25GB 且有授权限制 → 学会梳理数据合规与获取路径。

### 改进方向
- 用真实病例数据做准确率评测，沉淀评测集。
- 接入大模型做多轮对话与自然语言报告生成（V2 Agent）。
- 症状标准化升级：接入更完整的中文 ICD/SNOMED 术语映射。

## 7. 从"工具"到"AI Agent"的演进（对接你投的 AI Agent 产品经理岗）

当前系统本质是"**规则编排式智能体**"：感知（症状输入）→ 理解（CUI 标准化）→ 推理（模型+知识库）→ 输出（报告）。这已经是 Agent 的最小闭环。

升级路径：
1. **工具化**：把 5 个 API 定义为 Agent 的 Tool（validateSymptom / predict / sySuggest / getDetails）。
2. **编排**：LLM 作为"大脑"，自主决定调用哪些工具、按什么顺序（ReAct / Function Calling）。
3. **记忆**：多轮对话中维护"已确认症状"上下文。
4. **知识增强**：RAG 检索 UMLS/医学指南，回答"为什么这个病概率高"。
5. **评估**：设计"诊断报告完整率、症状识别率、推荐采纳率"等 Agent 评测指标。

这套"感知-理解-推理-行动-评估"的 Agent 方法论，是可以直接写进简历和面试的。

## 8. 方法论沉淀（可复用的能力）

- **MVP 思维**：先做最小可用闭环（4 个查询功能），再迭代成一键诊断。
- **标准化优先**：任何领域 AI 产品，先解决"概念唯一标识"（本项目的 CUI），后续所有功能才可复用。
- **可解释性设计**：给用户的不只是结论，还有概率、依据、详情。
- **合规前置**：医疗类产品一开始就考虑授权、免责、隐私。
- **工程化**：Docker 化、端口/环境问题排查、一键启动脚本。
